# API v2 implementation history

How the [protocol 2 contract](../api/index.md) was built, phase by phase, on `feat/api-v2`. This page is a record: the contract pages under [Automation](../api/index.md) describe what ships, and where they and this page differ, they win.

## Strategy: build beside v1, switch once

Protocol 2 is a clean break for users, but `develop` must stay releasable between PRs. So:

- **v2 grows next to v1.** `ControlSession` dispatches by the negotiated version. Until the switch, `protocolVersion: 2` is accepted only when the app runs with `--automation-v2` (development builds and tests); release builds keep answering `UNSUPPORTED_VERSION` for 2. v1 code isn't touched except to share helpers.
- **One method catalog drives everything.** Each v2 method is declared once (name, parameter schema, result type, capabilities and conditional rules, scope rule, mutating/destructive flags, error codes). Authorization, MCP tool schemas and annotations, CLI help and the contract tests are generated from it, which is what prevents v1's schema drift.
- **The domain adapter is split by area.** `AutomationService.swift` (1,135 lines) becomes `Automation/V2/` files per area (`Workspace`, `Panes`, `Sessions`, `Agents`, `Remote`, `Projects`, `Tasks`, `Projection`), each calling the existing `AppWorkspaceModel` actions so the UI and API stay one path.
- **One branch, one PR, one commit per phase** (`feat/api-v2`), each commit following the [change workflow](../development/workflow.md): contract updated if the phase finds a gap, tests (observable behavior and failure safety), format, lint, build, test, independent review, `status.md`. Every commit builds and passes the full suite on its own.
- **Open points use the draft's defaults** (fixed agent response keys, `created`/`all` scope for new spaces, layout v3 refusing `windows`, migrated grants gain nothing) and are revisited in review.
- **The switch (phase 8)** removes v1, makes v2 the only protocol, and ships the CLI, MCP and migration together.

## Progress

**Phase 1 — Foundations (landed on `feat/api-v2`).**

- `--automation-v2` gives `AuthorizingControlHandler` a v2 domain (`AutomationServiceV2`); without it nothing changes, and `protocolVersion: 2` is `UNSUPPORTED_VERSION` exactly as before. With it, `auth.authenticate` accepts 1 or 2 per connection, other versions get `details.supported: [1, 2]`, and `control.json` keeps `protocolVersion: 1` (what the shipped CLI reads) and adds `protocolVersions: [1, 2]`.
- A v2 connection resolves names only in the catalog (`MethodCatalogV2`, `Sources/TrellisControl/V2/`), never v1 names or aliases; a v1 connection never sees v2 methods. Error replies use the v2 `data` shape once a client has asked for protocol 2.
- Each method is one `MethodSpecV2` value: parameters, capabilities and conditional rules, resource scope, all-spaces, mutating/destructive and revision target, error codes, summary. Validation (`-32602` with `data.fields`), authorization (`details.missing` on `PERMISSION_DENIED`), idempotency, MCP schemas and annotations (`MCPTools.v2`, served from phase 8) and CLI help (`synopsis`, `helpText`) are generated from it. The contract test refuses a declaration whose UUID parameter has no resource rule (unless marked `unscoped`), so a forgotten scope check can't fail open. List cursors are signed per app instance, so an edited, hand-built or previous-launch cursor is `INVALID_CURSOR`.
- The catalog holds `system.info` and `grant.get`. Until grant schema 2 (phase 3) the grant view shows v1 capabilities under their v2 names and omits `preset`, `revision` and the `projects` and `agents` scopes.
- The CLI keeps its v1 exit-code map until phase 8; `APIErrorCode.cliExitStatus` is the v2 map it will switch to (it differs for `UNSUPPORTED_VERSION`, `INVALID_CURSOR`, `INVALID_STATE` and `CLOSE_PENDING`).

**Phase 2 — Core resources (on `feat/api-v2`).**

- The catalog holds 39 methods: `workspace.get/save`, `space.*`, `tab.*` (with `tab.duplicate`), `pane.*` (first-class, with `pane.list/get`), `session.*` (with `session.stop`; `session.execute` without `wait`, which is phase 7) and `host.*` (with `host.connect {placement}`). The declarations are in `MethodCatalogV2+Core.swift`; the adapter is `Automation/V2/AutomationServiceV2+Spaces`, `+Tabs` (tabs and panes), `+Sessions` and `+Hosts`, each calling the same `AppWorkspaceModel` automation paths v1 uses. v1 is unchanged.
- The catalog stays declarative: `.structure` parameters with tagged-union variants (`launch`, `placement`) are validated field by field (`data.fields` names `launch.executable`) and generate closed nested MCP schemas; conditions are `present`, `provided` (null counts), `equals`, `contains` and `anyOf` over dotted paths; `rules` add at-least-one (update methods) and exactly-one (`text`/`base64`, `tabId`/`spaceId`); `allSpacesIf` makes all-spaces scope conditional (`host.connect` into a new space); resource rules reach nested IDs (`launch.hostId`, `placement.spaceId`). `problems(in:)` checks each of these (unknown paths, impossible values, variants naming undeclared fields, nested UUIDs without a resource rule, revision targets without a kind).
- `expectedRevision` is enforced by the dispatcher from each method's `RevisionTargetV2` and a `revision(of:)` lookup on the domain, inside the idempotent execution (a replay still returns its first result), and checked again on the main actor just before the adapter acts. Space, tab and workspace targets are also passed to the store, which compares atomically with the change; pane and session revisions are kept by the model (`AutomationRevisions`, stamped from each published snapshot and on maximize) and are check-then-act on the main actor. A contract test sends a stale revision to every mutating method and checks `CONFLICT` before the domain sees it. `workspace.save` and `host.create` are the only exemptions.
- UUID parameters, nested ones included, are lowercased during validation, so a retry that spells an ID in another case replays instead of conflicting with its idempotency key.
- Projections (`ProjectionV2`, in TrellisControl) are pure functions of the snapshot, a `RuntimeV2` captured from the model in one main-actor pass, the saved hosts and the grant, so they are tested over hand-built workspaces for every machine and launch kind. `workspace.get` with 100 panes takes about 20–35 ms end to end in tests (bound 500 ms); a reply over the frame is `LIMIT_EXCEEDED`.
- `session.start` refuses `launch.kind: "agent"` with `-32602`; starting an agent pane's saved launch is `PERMISSION_DENIED` with `details.missing: ["agent.control"]` until grants can hold it (phase 3). `start: true` on create methods checks the same saved-launch rules (agent, host scope) before anything is created, so `tab.duplicate` of an agent or SSH tab can't start what `session.start` would refuse.
- Not yet supplied, by design of the phase: a space's `project` has only `id` and `missing` (its `name`, `target` and `folder` need **project.read**, which grants hold from phase 3, and the project projection of phase 7); `workspace.get` refuses `include: ["agents"]` until phase 5; a host's `remote.link` has no `reason` for `needsInput` and `disconnected`, because the app keeps it only as UI text in the user's language (phase 6 adds machine-readable reasons); there are no v2 events yet (phase 4).
- Contract changes found while building: the pane `attention.bell` flag was dropped (a bell is `needsInput: "attention"`, FR-T06); `pane.resize` compares its tab's revision and `host.connect` its host's; `host.list` and `host.delete` carry no container or workspace revision; live status doesn't move a revision, and pane and session revisions restart after a relaunch; the launch descriptor shapes and the `session.stop` force rule are spelled out in [Methods](../api/methods.md#sessions).

**Phase 3 — Permissions and grants (on `feat/api-v2`).**

- Grants store v2 capabilities, a preset, a revision and four scopes (`AutomationGrant`, `GrantStore.swift`). `grants.json` is schema 2; a schema 1 file is migrated on first load to exactly the mapped capabilities (preset `custom`, every project and agent), after a byte-for-byte `grants.json.v1.bak`. This ships ahead of the switch because the new grant sheet edits grants, so protocol 1 reads its view of the same records: `capabilities` maps the stored v2 set back to v1 names and hides the new areas, which keeps every v1 test unchanged. The only tests that changed pinned the old file format (`windowScope` in `SpaceAliasTests`, a v1 capability name in the unreadable-file test) or phase 2's partial grant view.
- `created` scope: `CallV2.recordCreatedSpace` writes the creating grant into a lock-protected ledger owned by the grant store, from inside the `then` follow-up of the store transaction that creates the space (`space.create`, `host.connect` into a new space; `remote.open` and `project.launch` will do the same). Nothing (a later call, the call's own projections through `CallV2.grant`, an event) can see the space before its grant does. The ledger is saved with the grants in the background and pruned after a `space.deleted` event has been delivered (`EventForwarder`'s `delivered` hook in `AppMain`). Protocol 1 sees `created` as that set of spaces and, needing all spaces to create one, never adds to it.
- The catalog gained `anyOf` capability groups (`agent.respond` or `session.input`, reported as `agent.respond` in `details.missing`), `createsSpace`/`createsSpaceIf` (all or `created` scope, replacing `allSpaces` on `space.create` and `allSpacesIf` on `host.connect`), and `project` (UUID) and `agent` (string) resource kinds checked against the project and agent scopes, so phases 5 and 7 only declare them. A saved agent launch (`session.start`, `start: true`) needs agent.control and the agent in scope; phase 2's interim refusal is gone. A project space's `project` field is shown only for projects in scope.
- Edits (`GrantStore.update`) bump the revision and never touch the token. A widening edit needs `confirmedWidening` and is saved before it applies; a narrowing one applies first and raises `reauthenticateBelow`, so connections that authenticated earlier (their `ControlIdentity.grantRevision`) get `AUTH_REQUIRED` once on v1 and v2 alike. `onEdit` observers end subscriptions `events.subscribe` would now refuse and MCP sessions of the grant; that observer is where phase 4 emits `grant.changed`. Until that observer runs, event delivery re-checks the grant's capabilities per event and MCP's `tools/list` refuses a stale authentication. `approveHosts` (Reapprove) only refreshes hosts the grant already approved; adding a host is a confirmed widening.
- The grant sheet (`AutomationSettingsView`, `GrantDraft`) leads with the five presets, groups every capability by area with localized plain-language descriptions (the raw name as a caption), picks spaces (all, created, chosen), projects, hosts and agents, and edits active grants; widening shows a confirmation whose Cancel leaves the grant unchanged. Composition rows whose methods arrive in later phases are tested through sample declarations of their documented shapes (`PermissionsV2Tests.composed`).
- Contract changes found while building: preset default scopes for hosts, projects and agents; how `created` is recorded, kept and pruned, and what protocol 1 sees; narrowing vs widening, which edits end authentications, and that only active grants are editable; the schema 2 layout; and that schema 2 lands before the switch, so an earlier release can't read it (restore the backup). Pending: the grant sheet in the native app and with VoiceOver.

**Phase 4 — Events (on `feat/api-v2`).**

- Protocol 2 has its own typed stream, `EventHubV2` (`Sources/TrellisControl/V2/EventHubV2.swift`): its own sequence and a ring of 2,000, beside protocol 1's `EventHub`, which is untouched (its topics, ring of 1,000, string data and aliases, and every v1 test). Both are fed by `EventForwarder`'s one FIFO consumer; each published transition goes to v2 before v1, so a closed space leaves `created` scopes (pruned after v1's batch) only once both streams delivered its `space.deleted`. A publish whose work another drain picked up returns only after it was delivered, so that ordering holds under concurrency.
- Sources: workspace, selection and session events come from `WorkspaceDiffV2` (pure, run off the main actor on the forwarder's task) over each published transition, which adds `changed` field names, `tab.reordered`, typed numbers, `session.replaced` (a pane's session changed: restart) and `session.launchChanged` (same session, new launch: `configureStoppedSession`, agent restart, host connect); protocol 1's `WorkspaceEvents.diff` is unchanged. Live state comes from `didSet` on the model's runtime dictionaries (`inputWaits`, `progress`, `busyTabIDs`, `agentStates`, `agentAvailability`, `remoteMissingAgents`, `taskRuns`, `remoteLinks`, `maximizedPanes`) and from `applyShellEvent` (`AppWorkspaceModel+LiveEvents.swift`), so every writer is covered and nothing runs per output chunk; each emitter returns at once while `onLiveEvents` is nil (always, without `--automation-v2`). Project launches are reported where the launch flow ends, hosts and projects from their list models' refreshes (after the first load), the helper status from `RemoteHostsModel.preferences`, appearance beside v1's event, and `grant.changed` from the grant store's `onEdit` observer in `AppMain`, before any revalidation.
- Coalescing happens in the hub (`ContinuousClock`, 250 ms per resource and type for `pane.needsInput`, `pane.progress`, `tab.busy`, `agent.state`, `agent.settings`); shell events are one per mark. A test drives a program reporting progress as fast as it can (hundreds of reports a second) and finds at most one event per window plus the final state; another runs `yes` for two seconds through a real PTY and finds a handful of events in all.
- Redaction is one function, `EventDraftV2.data(for:)`, used by push, replay and poll against the grant re-read at delivery: topic capability, space scope (created included; `space.reordered` needs all spaces), host scope (current connection for `remote.*`, approval for `host.*`), project scope, per-field rules (`path` and `folder` need session.execute, a launch's `hostId` the host), and `grant.changed` only to its grant. Subscriptions keep the v1 rules: narrowing ends those whose topics the grant may no longer follow (after its `grant.changed`), others are filtered per event (API2-06d).
- `events.subscribe`, `events.unsubscribe` and `events.poll` are catalog methods (`MethodCatalogV2+Events.swift`) whose capabilities are conditional on the topics asked for, so `details.missing` and MCP visibility come from the declaration; subscribe and unsubscribe are marked socket-only and aren't MCP tools. `events.poll` long-polls in the hub (a continuation woken by the next publish, the deadline, a revocation or cancellation), at most 4 waiting per grant; `ControlSession` answers a waiting poll out of order through the server's outbox, so the connection keeps serving later frames, and closing it cancels the poll. The dispatcher path is transport-agnostic, ready for MCP's `events_poll` in phase 8.
- Tests: `EventsV2Tests` (envelope, ring and gap, cursors, poll timing at 500 ms / 2 s, the per-grant bound, cancellation, the redaction matrix, serialized events without command text, subscriptions with topic capabilities, narrowing, replay without duplicates, output, coalescing, the diff, host and project library changes) and `AutomationV2EventTests` over the real model (each live source within 250 ms, restart and reconfigure, created-scope and execute redaction, `yes`, `events.poll` on a v2 connection, `grant.changed`, a project launch); `EventsV2ReviewTests` (a closed `created` space's last events stay pollable by its grant, pending live status precedes the event that ends its resource).
- Gaps, recorded rather than faked: `remote.link` has no `reason` (UI text until phase 6), and `agent.availability` on a host only says `missing` (found by a failed launch) or `unknown`. Task runs are reported from the UI's runner (`taskRuns`); `task.*` methods arrive in phase 7. `pane.updated` doesn't report pane moves within a tab (a layout change is `tab.layoutChanged`).
- Contract changes found while building: the v2 stream is separate from v1's; the `data` of every type, `cleared: true` for attention, `phase: cancelled` for task runs, `resource` without an `id` for workspace-wide events; `nextSequence` and gap semantics for polls, `INVALID_CURSOR` for another instance, the 4-poll bound, polls never returning output, subscriptions being socket-only; host events needing approval at all versus the current connection for remote ones; replayed shell marks producing no events.

**Phase 5 — Agents (on `feat/api-v2`).**

- The catalog holds the seven `agent.*` methods (`MethodCatalogV2+Agents.swift`); the adapter is `Automation/V2/AutomationServiceV2+Agents.swift`. `agent.start`, `agent.restart` and `agent.install` use the store commands and start path of the app's Agents view, Restart and Install and Launch: the new tab or split and its agent launch are one store transaction (`createTab`/`splitPane` with a `configureStoppedSession` follow-up), a finished pane gets a fresh session through `automationRestart`, and the agent starts through `automationStartSession`, so `startAgent`, the hook wiring, the broker and remote helpers, the 127 install offer and the live events are the app's own. The model gained only small shared pieces: `agentInstaller(_:hostID:)` and `agentPlatform(hostID:)` (also used by the install offer), `forgetMissingAgent` (also used by `installAgent`), `agentStateSince` for a run's `since`, and definition revisions in `AutomationRevisions`.
- `RevisionTargetV2.anyResource` lets a method compare `expectedRevision` with whichever placement ID is sent (the space for a new tab, compared atomically by the store; the pane for a split or a pane); the contract checker requires each to be a UUID field with a resource rule. `agent.restart` and `agent.respond` compare the session's revision.
- `agent.respond` is the first real `anyOf` (agent.respond or session.input); `DispatchV2Tests` denies it with neither (`details.missing: ["agent.respond"]`) and allows either alone, and the walker that checks every method's `PERMISSION_DENIED` now reports `anyOf` groups. The fixed keys (the draft's default) are `1` + Return, Escape, and the text + Return; the text is one line without control bytes, the state check (`needsInput` or `expectedState`) runs on the main actor right before the bytes go through `session.sendInput`'s path (host scope, `REMOTE_DISCONNECTED`, queue limits), and approve and reply count as the user's Return for the run's state.
- `workspace.get` accepts `include: ["agents"]` and returns `agentRuns`. Runs are panes whose current session has live agent state (a typed agent once its hooks spoke, FR-AG18), in sidebar order and space scope; definitions are readable whatever the agent scope.
- Events needed no new source: API-started agents go through the same `agentStates`, `agentAvailability` and `remoteMissingAgents` writers, so `agent.started`, `agent.state`, `agent.ended` and `agent.availability` arrive for them (tested end to end).
- Tests: `AutomationV2AgentTests` over the real model with a fake login shell and an agent that prints every byte it reads (start in a tab, split and pane, folders, the exact bytes of approve, reject and reply, stale and refused answers sending nothing, restart and resume, `AGENT_UNAVAILABLE` with and without an installer, an install whose installer creates the agent, a 127 launch marking it missing, detected runs, a remote workspace's host scope, availability and `REMOTE_DISCONNECTED`, capabilities, agent and space scope, a stale space revision leaving no tab, idempotent replay, and the events); `RemoteWorkspaceTests.testAgentStartThroughTheAPIRunsTheAgentOnTheHost` starts an agent on a host through the real helper over the fake `ssh`; projection tests for definitions (redaction of `executable` and `install`, hosts outside scope) and runs; the catalog, contract and composition tests now use the real declarations.
- Gaps, recorded rather than faked: a host's availability is still only `missing` (from a launch) or `unknown`, and this Mac's only what its last PATH check found (reads don't start a check, the app's Agents view does); `agent.install` returns when the installer's pane has started, and its outcome is observed through the run and `agent.availability`, not awaited. Pending (manual): real Claude Code, Codex and pi answered through `agent.respond`, and the vendor installers through `agent.install` on a clean Mac and a Linux host.
- Contract changes found while building: `agent.install` takes a `placement` instead of `hostId` (the app's installer runs in a visible pane and then starts the agent, so it needs a pane, and the composition row gains agent.control and workspace.write); a `pane` placement accepts finished panes, not only stopped ones; results add `session` (so a run that already ended still says how) and `acceptedBytes` for `agent.respond`; `agent.list` is paginated and takes a `machine` filter; definitions add `resumable` and `install` (execute) and the `unknown` status; runs add `spaceId`, and `settings.model` is the reported model ID, as in events; `AGENT_UNAVAILABLE` means *known* missing, with `details.agentId`, `machine`, `install` and `requires`; agent scope hides agents from the start methods only.

**Phase 6 — Remote workspaces (on `feat/api-v2`).**

- The catalog holds `remote.open`, `remote.status`, `remote.reconnect`, `remote.helper.install` and `remote.helper.remove` (`MethodCatalogV2+Remote.swift`); the adapter is `Automation/V2/AutomationServiceV2+Remote.swift`. They are the app's own paths: `remote.open` the store's `createRemoteSpace` and the pane start of **Open Remote Workspace**, `remote.reconnect` the reconnector's attempt behind **Retry Now** and **Reconnect…**, the helper methods `RemoteHostsModel`'s install and remove behind the host library's actions (which now return an `ActionResult` the library turns into the same messages as before). `remote.open` declares `createsSpace` and records the space for a `created` grant inside its store transaction. Reconnecting and the host-library actions gained an optional install-policy override and return their failure; `startRemote`'s connection step became `remoteConnection`, shared with the API.
- **Reason codes.** `RemoteLinkReason` (TrellisCore) is the one list of codes. `RemoteHostLink.Failure.reason` derives a code from each structured failure; `RemoteSSHDiagnosis` now also says what an automatic attempt needs (`authFailed`, `needsPassword`, `needsPassphrase`, `hostKeyChanged`, `hostKeyUnverified`, `needsInput`) and `Failure.needsInput` carries it. `RemoteLinkDisplay`'s `needsInput` and `disconnected` keep their words for the sidebar and carry the code beside them (`closed` after quit or Close All Workspaces, `hostMissing` for a deleted host), so the UI's text and behavior are unchanged. `Host.remote.link.reason`, `remote.link` events and remote error details use the code, never the words.
- **helperInstall rule.** A connection the API makes uses `.always` when the host's auto-install is on or the grant holds remote.manage, otherwise `.never`; a probe that finds no helper then ends as `declined`, which the adapter turns into `CONFIRMATION_REQUIRED` (`helperInstall`) before anything is created. The app's install sheet, remove and stop-sessions confirmations are never shown for an API call (the tests fail if they are).
- **Connecting for other methods.** Starting a session on a remote workspace host whose link is down (session start and restart, `start: true`, agents) connects first through the same path, as an automatic attempt (BatchMode), so a failure is `REMOTE_DISCONNECTED` with its reason and nothing is created. Agents there also need a helper of protocol 3 or later, checked before anything is created (`helperTooOldForAgents`).
- **Not blocking.** The remote methods are declared `waits`; `ControlSession` answers them out of order through the server's outbox, as it does a waiting `events.poll` (at most 16 waiting per connection, then in order), so ssh asking the person in the console or a helper upload never holds up the connection's later calls; every wait is an `await` off the main thread's run loop. `remote.reconnect` returns when its attempt ends; later automatic attempts are reported by `remote.link` events.
- **Host access for remote sessions (decision).** FR-RW15 is applied to every session method that acts on a remote workspace session or reads its output: `session.stop` and `session.readOutput` now need the host in scope, like start, restart, input and execute already did (and `agent.restart`, `agent.respond`). Records stay readable by space scope with the host's ID redacted, as before. `session.stop` and restarting a running session are `REMOTE_DISCONNECTED` while the link is down, like input. `REMOTE_DISCONNECTED` became `sometimes` retryable: a down link and an unreachable host are retryable, a host that needs the person isn't.
- Tests: `AutomationV2RemoteTests` over the real model with the fake `ssh` and the real helper, bridge and broker: open with start in a `created` scope (shell on the host, installed with remote.manage and no sheet, status and host link, space hidden from another created grant), the helperInstall refusal leaving no space, tab or file on the host and the host's auto-install letting `session.start` proceed, helper install and remove (running sessions refused, `stopSessions` needing session.close), Retry Now and Reconnect… with `reconnecting`, `needsInput`/`authFailed` and a resumed pane, input and stop refused while down, an interactive failure (`sshExited`) and a classified automatic one (`hostKeyChanged`), host and space scope, stale approvals and revisions, every session method on a remote session of a host out of scope, and an `agent.install` (and the app's Install and Launch) refused after the installer mark was set leaving no stale mark. `RemoteV2Tests` (declarations, out-of-order answers, the 16-call cap and no reply after close), reason unit tests (`RemoteHostLinkTests`, `RemoteReconnectPolicyTests`), projections, events with reasons (`AutomationV2EventTests`), and the composition rows now use the real declarations.
- Gaps, recorded rather than faked: a host's agent availability is still only `missing` (a launch exited 127) or `unknown`: the helper reports no installed agents and finding them would mean running a login shell there, so it stays a later protocol change. The `helperTooOldForAgents` refusal needs a helper older than protocol 3 and has no automated test. Pending (manual): a real host through `scripts/test-remote-docker.sh` driven by the API, and password, passphrase and host-key prompts answered in the console during `remote.open` and `remote.reconnect {interactive}`.
- Contract changes found while building: `remote.reconnect` takes `interactive`; `remote.helper.remove` takes `stopSessions` (+session.close) and is refused with `runningSessions` like the app, not because a workspace is open; `remote.open`'s `start` defaults to false, connects before creating, and its revision is the workspace's; reason codes and their table; `helper: "unknown"`; `REMOTE_DISCONNECTED` retryable `sometimes`; the host rule for every session method.

**Phase 7 — Projects and tasks (on `feat/api-v2`).**

- **`ProjectLauncher` (the sheet-free launch path).** `Sources/TrellisUI/ProjectLauncher.swift` holds what the launch sheet did inline: `plan` (resolve and check the target), `startSetup` (the setup terminal on this Mac or the host) and `open` (plan the layout, apply it with the project binding, queue commands, make agent panes, start the created panes, record the launch and emit `project.launched`). The sheet (`beginProjectLaunch`, `checkProjectLaunch`, `runProjectSetup`, `openProjectLaunch`, `cancelProjectLaunch`) keeps its stages and calls it; `ProjectLaunchFlowTests` and `RemoteProjectLaunchTests` pass unchanged. Only how a host is reached differs: the sheet's launcher connects with the console and the app's install policy (`projectHostConnection`), the API's takes the link `readyRemoteLink` made ready first under the helperInstall rule. `automationApplyLayout` gained a `then` follow-up so a launch records its new space for a `created` grant inside the store transaction.
- The catalog holds `project.list/get/create/update/delete/capture/check/launch` and `task.list/get/run/stop` (`MethodCatalogV2+Projects.swift`); the adapter is `Automation/V2/AutomationServiceV2+Projects.swift` and `+Tasks.swift`. `MethodSpecV2.waitsIf` lets a method wait only with some parameters: `session.execute` with `wait`, `project.check` on a host and `project.launch` on a host or with `setup` are answered out of order (sharing the 16-per-connection budget with `events.poll`), while the same methods without them keep the connection's order; `waits` stays the four remote methods.
- **Projects.** The library is mutated through `ProjectListModel` (the window's model), so the window and the `project.*` events follow API changes; `ProjectListModel.isLoaded` mirrors `ProjectLibrary.isLoaded`, and a space's `project.missing` is computed only from a loaded library (an unloaded or unreadable one calls nothing missing). `space.project` now has `name` and `target` (project.read) and `folder` (session.execute), the folder read from the launch's binding namespace. Revisions: `project.update`/`delete`/`launch` compare the project's `revision` (the one `project.check` returns in its plan); `project.create` and `project.capture` are exempt like `host.create`. A launch checks what the definition runs before anything runs (session.execute for commands, agent.control and agent scope for agent panes via `requireLaunchAccess`), connects a host first, refuses setup without `setup: true` (`SETUP_REQUIRED` with the plan), re-checks the revision after setup (`CONFLICT`), refuses to reconcile a space outside the grant's scope, and drops any installer mark on the agent panes it starts.
- **Setup through the API** runs `startSetup` in a terminal kept in `automationSetupTerminals` (so a host's link stays wanted and its hangup is delivered, as for the sheet's), with `GIT_TERMINAL_PROMPT=0`, a 15-minute bound and a hangup-then-kill on timeout or cancellation; anything but exit 0 is `LAUNCH_FAILED` with `details.setup`.
- **Tasks** read the pane's catalog through `loadTaskCatalog(paneID:)`, shared with the Tasks view's refresh but without touching its catalog; typing goes through `startTask` (extracted from `typeTask`), so the API and the view type the same line into the same `taskRuns`, whose `didSet` already emits `task.run`. `pane.task` and `task.get` read that record.
- **`session.execute {wait}`** registers a `CommandWait` before typing and follows the next command start and its finish (or prompt) mark through `updateCommandWaits`, called from `applyShellEvent` beside the task runs; replayed marks are ignored. It needs authenticated integration and an idle prompt.
- Tests: `ProjectsV2Tests` (declarations and `waitsIf`, out-of-order execute waits, project, plan, task and space projections with redaction), `AutomationV2ProjectTests` (library CRUD through the list model with redaction, scope, revisions and failure safety; capture; check → `SETUP_REQUIRED` → launch with setup through a fake git into a `created` scope, relaunch reconciling, another grant refused; `CONFLICT` after an edit; commands, agents and agent scope; failed and stuck setups; `missing` only from a loaded library), `AutomationV2RemoteProjectTests` (fake ssh and the real helper: `remote.connect` needed, host scope, the helperInstall refusal leaving nothing behind, then check and launch with setup on the host into a space bound to host and project), `AutomationV2TaskTests` (list with redaction and scope, run as Run does with integration required, untrusted `launch.json` tasks until trusted in the app, stop and force, the shared `taskRuns` and its events, `session.execute {wait}` exit code, busy, timeout and `noIntegration`); the catalog, contract, dispatch and composition tests now use the real declarations (the composition rows that depend on a project's contents run over the real model).
- Gaps, recorded rather than faked: setup through the API can't answer a passphrase, password or host-key prompt (it runs where nobody sees it; set such projects up from the app); a wait's command is matched by order, so a line typed by someone else at the same prompt could be taken for it, as with task runs. Pending (manual): a project launch with clone and setup on a real host and repository; the API's launch in the native app.
- Contract changes found while building: the plan's fields and `revision`; `launches`' shape; `project.check` needs remote.connect for a host target (it connects); `folder` on a launch needs session.execute; `project.update` gates folders too; `project.create`/`capture` exempt from `expectedRevision`; `warnings` on capture; `task.list`'s `file` and the task ID scheme (`file:`/`detected:`); `task.get` omits `run` when there is none; `task.stop`'s force rule; `session.execute`'s `sessionEnded`, the `busy` refusal and its ordering note. **Phase 8 — Layout v3, CLI, MCP and the switch (landed on `feat/api-v2`).**

- **The switch.** Protocol 2 is the only protocol on the socket, the CLI and MCP. Protocol 1's dispatch, its authorization table, its domain adapter (`AutomationService.swift`), the `window.*`/`windowId` aliases and its event hub (topics, ring of 1,000, string data) are removed; shared infrastructure (framing, discovery, peer UID checks, rate limits, idempotency, output cursors) stays and its tests were ported. `--automation-v2` is gone. `control.json` reports `protocolVersion: 2` without the transitional `protocolVersions` list, and `auth.authenticate` with any other version is `UNSUPPORTED_VERSION` with `details.supported: [2]`.
- **Layouts, themes and appearance** joined the catalog (`layout.validate/plan/apply/export`, `theme.*`, `appearance.*`). Layout documents are version 3: spaces may carry `machine` and `projectId`, panes an `agent`, and launches name `ssh` instead of `host`; versions 1 and 2 are read as 3, except a `windows` list, which is refused. `layout.apply` checks what a document's contents need (remote.connect, project.launch, agent.control) and answers `PERMISSION_DENIED` with `details.missing`. Namespaces keep the key pattern, so layout bindings never reach project launches' bindings in the same `layout-bindings.json`.
- **CLI.** `trellis` speaks protocol 2 only, with the nouns in [Migration](../api/migration.md#cli) (`workspace`, `grant`, `agent`, `remote`, `project`, `task`, `events poll`, `session execute --wait` exiting with the command's code), exit codes from `APIErrorCode.cliExitStatus`, and names resolved server-side through filtered lists (`space.list {name}`, `tab.list {title}`, `host.list {query}`, `project.list {query}`).
- **MCP.** Tools are generated from the catalog (schemas, descriptions and annotations), filtered per grant, with `events_poll` and the untrusted-data notice on results that can carry untrusted text. The `initialize` instructions point to `workspace_get` and `events_poll`. At most 8 calls wait at once across MCP (`events_poll` with a timeout, `session_execute` with `wait`, the remote and project calls that wait on a host or a setup), so waiting calls can't take all 16 connections: past the bound a poll answers at once and the others get `LIMIT_EXCEEDED`; a poll waits at most 25 s, inside the listener's 30 s limit. A result too large for both text and `structuredContent` keeps only the text, and JSON-RPC-level errors carry `data {code, message, retryable, details?}` as on the socket. Tailscale sharing (FR-RC01–RC09) is unchanged.
- **Docs.** The v2 pages moved up to `docs/api/`, merging what still applied from protocol 1's authorization, errors and output pages; this plan became this history page.
- **Smaller changes.** A layout space on a remote machine keeps `~` paths as written; the host's home replaces it when the pane starts on the host's link (`AppWorkspaceModel.hostPath`), since the home isn't known before connecting. A project setup through the API also sets `GIT_SSH_COMMAND="ssh -o BatchMode=yes"` unless the environment already sets `GIT_SSH_COMMAND` or `GIT_SSH`, so an ssh prompt fails at once instead of waiting out the 15-minute bound. `session.execute {wait}` no longer polls every 20 ms: a shell mark wakes the waiter at once, and the session's end, the deadline and cancellation are checked at least every 250 ms. `scripts/qualify.py` and `scripts/bench-renderer.py` speak protocol 2 and seed a schema 2 `grants.json`. The app doesn't yet offer to re-link a `trellis` command that points at another (older) copy of Trellis: such a binary answers with `UNSUPPORTED_VERSION` and a message to run `trellis cli install-link` from the new app, and **Install Command Line Tool…** replaces the link.
- Recorded rather than faked: the manual checks listed in [Status](../overview/status.md) (the grant sheet with VoiceOver, real agents through `agent.respond`, a real remote host and a real project launch through the API, Claude Code and Codex as MCP clients over loopback and Tailscale, upgrading a released `grants.json`). The `*V2` type names in the code were kept where renaming them wasn't low-risk.

## Risks and how each phase handles them

| Risk | Where | Handling |
| --- | --- | --- |
| Project launch lives in a sheet flow (`checking → ready → settingUp → opening`) | 7 | Extract a model-level `ProjectLauncher` used by both the sheet and the API before adding the method; the sheet's tests must still pass unchanged. Done in phase 7 (`ProjectLauncher.swift`). |
| `agent.respond` keys fit Claude Code but maybe not every agent | 5 | Phase 5 ships the fixed table (the draft's default); `respond` keys in the agent definition (a definition schema change) stay open for review. |
| Event volume from shell marks and output-driven agent `working` | 4 | Coalesce per pane (at most one `attention`/`agent` event per 250 ms), never per output chunk; a test bounds events per second under `yes`. |
| `created` scope and spaces created by the UI on the API's behalf (project and remote launches) | 3, 6, 7 | Record the creating grant on the space at creation (runtime map, persisted with the grant), and test that UI-created spaces never join it. |
| Grant edits racing in-flight calls | 3 | Every call re-reads the grant (as v1 does); edits bump the grant revision and close subscriptions that lost access before returning. |
| Main-actor load from `workspace.get` on big workspaces | 2 | Build projections from one snapshot pass; bounded by the frame limit with `LIMIT_EXCEEDED`; a test with 100 panes measures about 20–35 ms against a generous 500 ms bound, so slow CI machines don't flake. |
| Clean break surprises users | 8 | Release notes and `migration.md`; `UNSUPPORTED_VERSION` names v2; the app offers to re-link an outdated CLI. |
